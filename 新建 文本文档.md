# Android Camera 通用 AI BugFix Agent
## 总体架构、可行性分析与分阶段实施方案

你现在需要基于当前代码引擎已有能力，设计并逐步实现一套面向 Android Camera 项目的通用 AI Bug Debug / BugFix 系统。

## 一、项目背景

当前项目是手机厂商 Android Camera 相关代码，主要使用 Java/Kotlin，同时包含 Framework、HAL、Vendor、Camera App、算法、配置及其他多层代码。

当前代码引擎已经具备以下能力：

1. 可以搜索整个代码仓库。
2. 可以读取和分析代码。
3. 可以执行 shell 命令。
4. 可以编译代码。
5. 可以执行测试。
6. 已经通过 MCP 接入内部技术文档。
7. 已经存在 Skill 机制。
8. 已经存在 Workflow 机制。
9. 已经存在通过限定 System Prompt、工具范围和输出参数构建简易 Agent 的机制。
10. 已经存在云真机测试能力。
11. 可以连接 Bug 库，并根据 Bug ID 获取具体 Bug 信息。
12. 当前开发人员已经使用 Skill、MCP、Workflow 和简易 Agent 解决过一些问题，但 AI 对 Camera Bug 的真实根因定位准确率仍然不高。

目前存在的问题不是简单的“AI 不会搜索代码”。

核心问题是：

- AI 可能拿到了相关代码，但没有构建完整执行路径；
- AI 可能看到大量相关信息，但无法判断哪些是关键证据；
- AI 容易根据历史经验或 Skill 进行错误类比；
- AI 容易把“可能原因”当成“真实根因”；
- AI 缺少系统性的反证和实验机制；
- AI 修改代码后可能只验证原始 Bug，而没有检查正常功能是否被破坏；
- AI 可能在错误根因上花费大量上下文和工具调用；
- 目前缺少统一的 Debug Trace、Evidence、Hypothesis 和 Patch Validation 机制。

因此目标不是继续增加大量 Skill，而是建设一个**通用的、证据驱动的 Android Camera BugFix Agent**。

---

# 二、总体目标

最终系统应该支持：

```text
Bug ID
  ↓
获取 Bug 信息
  ↓
分析环境和版本
  ↓
建立初始问题模型
  ↓
自主调查
  ↓
搜索代码 / 文档 / Git / 日志 / 历史 Bug
  ↓
建立多个根因假设
  ↓
收集支持证据和反证
  ↓
判断缺失证据
  ↓
设计验证实验
  ↓
执行实验 / 云真机测试
  ↓
更新假设
  ↓
必要时推翻原有假设
  ↓
确认 Root Cause
  ↓
生成最小 Patch
  ↓
分析 Patch 影响范围
  ↓
编译
  ↓
验证原始 Bug
  ↓
云真机执行针对性测试
  ↓
执行影响范围回归测试
  ↓
比较 Baseline / Candidate
  ↓
检查是否破坏正常功能
  ↓
生成 Validation Report
  ↓
人工审核
  ↓
最终确认
```

核心原则：

> Agent 不需要一开始就知道正确答案，但必须知道下一步应该寻找什么证据。

# 四、四种现有能力的职责重新划分

不要让 Skill、MCP、Workflow、简易 Agent 互相竞争。

它们分别承担不同职责。

## 1. Workflow

Workflow 是整个 BugFix 生命周期的骨架。

负责：

- 状态管理；
- 阶段切换；
- 条件判断；
- Investigation Loop；
- 人工审批；
- Patch 阶段；
- Build；
- 云真机验证；
- Regression；
- 最终报告；
- 失败重试；
- 中断恢复。

Workflow 不应该预先规定每一个 Bug 应该搜索哪些代码。

---

## 2. General BugFix Agent

这是核心推理 Agent。

负责：

- 理解 Bug；
- 调查代码；
- 调查文档；
- 分析日志；
- 查看 Git；
- 建立 Hypothesis；
- 判断缺失证据；
- 决定下一步调查；
- 设计实验；
- 分析实验结果；
- 判断 Root Cause；
- 生成 Patch；
- 根据 Validation 结果继续修复。

它应该具有自主调查能力，而不是一个固定 Prompt 的问答 Agent。

---

## 3. MCP

MCP 是真实工程能力层。

继续使用现有 MCP，不重复建设。

主要包括：

```text
Bug MCP
Code MCP
Document MCP
Git MCP
Log MCP
Build MCP
Test MCP
Device MCP
Historical Case MCP
```

如果现有 MCP 已经实现相关能力，优先复用。

不要因为建设新 Agent 而重新开发已有工具。

---

## 4. 简易 Agent

用于边界清晰、结构化输出的任务。

第一阶段只建议考虑：

```text
Bug Context Analyzer
Root Cause Reviewer
Patch Reviewer
Test Plan Analyzer
```

不要把整个 Debug 流程拆成十几个互相传递上下文的 Agent。

---

## 5. Skill

Skill 降级为辅助知识层。

Skill 用于：

- Camera 生命周期知识；
- Camera HAL 调试方法；
- Perfetto 使用方法；
- Buffer 生命周期分析方法；
- 特定工具使用方法；
- 公司代码规范；
- 已验证的通用工程规则。

不要把每一个历史 Bug 都生成 Skill。

历史 Bug 更适合形成 Case Memory。

---

# 五、核心：Investigation Engine

整个系统最重要的部分是 Investigation Engine。

不能采用简单的：

```text
Bug
→ 搜索
→ 阅读
→ 猜原因
→ 修改
```

应该采用：

```text
Bug
→ Facts
→ Unknowns
→ Hypotheses
→ Evidence
→ Counter Evidence
→ Experiment
→ Result
→ Hypothesis Update
→ Root Cause
```

---

# 六、建立 Investigation State

不要仅依赖 Chat History 保存调查状态。

建立结构化状态：

```json
{
  "bug_id": "CAMERA-12345",

  "environment": {
    "product": "",
    "device": "",
    "android_version": "",
    "build": "",
    "commit": ""
  },

  "facts": [],

  "unknowns": [],

  "hypotheses": [],

  "evidence": [],

  "experiments": [],

  "decisions": [],

  "modified_files": [],

  "validation": {}
}
```

---

# 七、Hypothesis 模型

每个根因假设必须结构化保存：

```json
{
  "id": "H1",

  "description": "",

  "status": "unverified",

  "supporting_evidence": [],

  "contradicting_evidence": [],

  "missing_evidence": [],

  "predictions": [],

  "experiments": [],

  "conclusion": ""
}
```

状态建议：

```text
UNVERIFIED
SUPPORTED
WEAKENED
REJECTED
CONFIRMED
```

禁止 Agent 因为“感觉可能性很高”直接把 Hypothesis 标记为 CONFIRMED。

---

# 八、Evidence 模型

证据也需要结构化：

```json
{
  "id": "E001",

  "type": "source_code",

  "source": "",

  "location": "",

  "commit": "",

  "content": "",

  "claim": "",

  "supports": ["H1"],

  "contradicts": [],

  "confidence": "observed"
}
```

Evidence 类型至少支持：

```text
SOURCE_CODE
DOCUMENT
LOG
TRACE
GIT_HISTORY
TEST_RESULT
DEVICE_RESULT
CONFIG
HISTORICAL_CASE
```

必须区分：

```text
Observed Fact
Inference
Hypothesis
Conclusion
```

不能让模型把推测当成事实。

---

# 九、Investigation Loop

主 Agent 每一轮调查都必须回答：

```text
1. 我现在确定了什么？
2. 我现在不知道什么？
3. 当前有哪些根因假设？
4. 哪些证据支持它们？
5. 哪些证据反驳它们？
6. 当前最关键的缺失证据是什么？
7. 下一步应该执行什么动作？
8. 为什么这个动作能够区分不同假设？
```

下一步动作可以是：

```text
SEARCH_CODE
READ_CODE
SEARCH_DOCUMENT
READ_DOCUMENT
SEARCH_GIT
ANALYZE_LOG
ANALYZE_TRACE
SEARCH_HISTORY
RUN_TEST
RUN_DEVICE_TEST
CREATE_EXPERIMENT
REASSESS_HYPOTHESIS
REQUEST_HUMAN_INPUT
CONFIRM_ROOT_CAUSE
```

---

# 十、关键原则：实验必须具有区分能力

不要只要求 Agent：

> “再测试一下。”

而要求：

> “这个实验能够区分哪些 Hypothesis？”

例如：

```text
H1：旧 Session Callback 修改新 Session
H2：Surface 被提前释放
```

那么实验应该能够产生不同结果：

```text
如果 H1 成立：
旧 Session Callback 应该在新 Session 创建后修改状态。

如果 H2 成立：
应该观察到 Surface 生命周期异常。

如果实验结果同时支持两个：
继续设计新的区分性实验。
```

这比简单让 AI “多跑几个测试”更加重要。

---

# 十一、Root Cause Confirmation

只有满足足够证据时才能进入：

```text
ROOT_CAUSE_CONFIRMED
```

至少需要：

1. 根因能够解释 Bug 现象；
2. 有源代码或运行时证据；
3. 没有明显反证；
4. 至少存在一个能够验证根因预测的实验；
5. 实验结果与预测一致；
6. 当前主要替代假设已经被排除或明显弱化。

如果无法满足：

```text
ROOT_CAUSE_SUSPECTED
```

而不是强行进入 Patch 阶段。

---

# 十二、Patch Generation

Root Cause 确认后才能进入 Patch 阶段。

要求：

1. 修改尽可能小；
2. 只修改与 Root Cause 有关的代码；
3. 不进行无关重构；
4. 保留原有接口行为；
5. 尽量添加能够防止问题重新出现的测试；
6. Patch 必须能解释为什么能够阻断 Root Cause。

Agent 输出：

```json
{
  "root_cause": "",
  "patch_strategy": "",
  "modified_files": [],
  "modified_symbols": [],
  "expected_behavior": "",
  "risk": "",
  "required_tests": []
}
```

---

# 十三、Patch Impact Analysis

这是验证“有没有改坏其他代码”的核心。

Patch 生成后，不应该直接进入测试。

先分析：

```text
Git Diff
↓
Modified Files
↓
Modified Symbols
↓
Callers
↓
Callees
↓
Shared State
↓
Interfaces
↓
Configuration
↓
Affected Features
↓
Regression Test Plan
```

生成：

```json
{
  "modified_symbols": [],
  "affected_modules": [],
  "affected_features": [],
  "risk_level": "",
  "regression_tests": []
}
```

例如修改：

```text
CameraDeviceImpl.configureSession()
```

系统应该分析：

```text
Preview
Recording
Capture
Camera Switch
Session Recreation
Session Close
```

而不是只测试原始 Bug。

---

# 十四、Validation Engine

验证阶段必须独立于 Root Cause Agent。

核心原则：

> 主 Agent 负责提出修复，Validation Engine 负责证明修复是否成立。

不能让：

```text
Agent 修改代码
↓
Agent 自己测试
↓
Agent 自己判断 PASS
↓
Agent 自己宣布修复成功
```

作为最终验收机制。

---

# 十五、Baseline / Candidate 双版本验证

每个 BugFix 都必须明确：

```text
BASELINE
```

和：

```text
CANDIDATE
```

Baseline：

```text
修复前版本
```

Candidate：

```text
修复后版本
```

必须记录：

```text
Commit
Build Fingerprint
Product
Device
Android Version
ROM
Test Configuration
```

---

# 十六、第一步必须验证 Baseline

这是整个验证系统最重要的原则之一。

在修改前：

```text
运行原始 Bug 测试
```

确认：

```text
Bug 可以复现
```

或者：

```text
已知异常指标可以被观察到
```

如果 Baseline 无法复现：

```text
NOT_REPRODUCED
```

不能直接说 Candidate 修复成功。

---

# 十七、Candidate 验证

修改后：

```text
Build Candidate
↓
部署到云真机
↓
执行相同测试
↓
收集 Log
↓
收集 Trace
↓
收集测试结果
```

然后比较：

```text
Baseline
vs
Candidate
```

---

# 十八、云真机是核心验证环境

当前已经存在云真机，因此优先复用。

不要重新建设云真机系统。

需要让代码引擎能够通过现有接口完成：

```text
设备选择
↓
检查设备状态
↓
确认 ROM
↓
部署 Build
↓
执行 Camera Scenario
↓
收集 Log
↓
收集 Trace
↓
执行压力测试
↓
返回结构化结果
```

如果现有云真机能力已经通过 MCP 或其他工具提供，直接封装为 Validation Tool。

---

# 十九、Camera Test Scenario

不要只提供一个：

```text
run_test()
```

应该逐步形成标准 Camera Scenario。

例如：

```text
Preview
Photo Capture
Video Recording
Camera Switch
Open / Close
Session Recreation
Background / Foreground
Zoom
HDR
Night Mode
Flash
Concurrent Camera
Repeated Capture
Long Running
Thermal Stress
```

不同 Bug 根据 Impact Analysis 自动选择。

---

# 二十、偶现 Bug 的统计验证

对于偶发 Bug：

不能只运行一次。

系统应该根据 Baseline 的复现率自动决定测试次数。

例如：

```text
Baseline Reproduction Rate
+
Confidence Requirement
+
Test Cost
```

决定：

```text
Candidate Test Count
```

同时记录：

```text
Baseline:
Runs = N
Failures = M
Failure Rate = M/N

Candidate:
Runs = N2
Failures = M2
Failure Rate = M2/N2
```

不要因为 Candidate 跑一次成功就宣布修复。

---

# 二十一、Regression Test Selection

不能每个 Bug 都运行完整 Camera 回归。

建立：

```text
Test Impact Analyzer
```

输入：

```text
Bug
+
Root Cause
+
Git Diff
+
Dependency Information
```

输出：

```text
P0 Tests
P1 Tests
P2 Tests
```

规则：

```text
P0 = 直接相关功能
P1 = 修改影响范围内功能
P2 = 更大范围系统回归
```

例如：

```text
修改 Session Lifecycle

P0:
Camera Switch
Session Recreation
Preview

P1:
Recording
Capture

P2:
完整 Camera Regression
```

具体测试集合不能只由 LLM 猜测，应尽可能结合现有测试用例、代码依赖关系和工程配置。

---

# 二十二、Regression Verification

至少检查：

```text
原始 Bug
+
直接相关功能
+
修改代码的其他调用路径
+
共享状态相关功能
+
必要的系统级回归
```

例如：

```text
Preview       PASS
Recording     PASS
Capture       PASS
CameraSwitch  PASS
SessionClose  PASS
```

如果出现：

```text
Candidate:
Original Bug PASS
Recording FAIL
```

则：

```text
PATCH_REJECTED
```

并把 Regression Failure 返回 Investigation Agent。

重新进入：

```text
Investigation
```

而不是直接结束。

---

# 二十三、完整的闭环必须允许“修复失败后重新调查”

最终 Workflow 不是：

```text
Investigation
↓
Patch
↓
Test
↓
Finish
```

而应该是：

```text
Investigation
↓
Root Cause
↓
Patch
↓
Validation
     │
     ├── PASS → Regression
     │
     └── FAIL
            ↓
       Analyze Failure
            ↓
       Update Hypothesis
            ↓
       Investigation
```

因此：

**Validation Failure 本身也是 Evidence。**

例如：

```text
原始 Bug 消失
但是 Recording 出现异常
```

这意味着：

```text
Patch 引入新的副作用
```

这个测试结果应该进入 Evidence Store，并重新触发 Investigation。

---

# 二十四、Root Cause Reviewer

主 Agent 得出 Root Cause 后，不应该立即修改代码。

调用一个独立的简易 Agent：

```text
Root Cause Reviewer
```

输入：

```text
Bug
Facts
Evidence
Counter Evidence
Hypotheses
Experiments
Proposed Root Cause
```

要求输出：

```json
{
  "decision": "APPROVE | NEED_MORE_INVESTIGATION | REJECT",

  "missing_evidence": [],

  "contradictions": [],

  "alternative_hypotheses": [],

  "recommended_experiment": ""
}
```

Reviewer 应该尽量使用独立上下文。

不能简单把主 Agent 的完整推理历史原封不动给 Reviewer，否则容易形成“互相确认”。

---

# 二十五、Patch Reviewer

Patch 生成后，再调用一个独立的 Patch Reviewer。

检查：

```text
是否修改无关代码？
是否存在不必要重构？
是否扩大影响范围？
是否改变 API 行为？
是否存在并发风险？
是否存在生命周期风险？
是否遗漏异常路径？
是否添加足够测试？
```

输出：

```json
{
  "decision": "APPROVE | REJECT | NEED_REVIEW",
  "risks": [],
  "affected_features": [],
  "missing_tests": []
}
```

---

# 二十六、最终 Validation State

不要只有 PASS / FAIL。

建议：

```text
NOT_REPRODUCED

ROOT_CAUSE_SUSPECTED

ROOT_CAUSE_CONFIRMED

PATCH_BUILT

FIX_VERIFIED

REGRESSION_PASSED

PARTIALLY_VERIFIED

PATCH_REJECTED

VALIDATION_BLOCKED
```

只有：

```text
ROOT_CAUSE_CONFIRMED
+
FIX_VERIFIED
+
REGRESSION_PASSED
+
PATCH_REVIEW_APPROVED
```

才允许最终状态：

```text
FIX_VERIFIED
```

如果某些测试没有执行：

```text
PARTIALLY_VERIFIED
```

而不能显示：

```text
PASS
```

---

# 二十七、Debug Trace

整个流程必须记录完整 Trace。

至少记录：

```text
Bug Input
Tool Calls
Tool Arguments
Tool Results
Retrieved Code
Retrieved Documents
Hypotheses
Evidence
Experiments
Experiment Results
Agent Decisions
Patch
Build Result
Device Test Result
Regression Result
Final Decision
```

目的是以后可以回答：

```text
AI 为什么认为这是 Root Cause？
它看到了什么？
它搜索了什么？
它漏掉了什么？
它什么时候产生了错误判断？
哪个工具返回了错误信息？
哪个阶段导致了最终失败？
```

这是后续优化准确率的基础。

---

# 二十八、Failure Analysis

每个失败任务必须自动分类：

```text
RETRIEVAL_FAILURE

CONTEXT_FAILURE

REASONING_FAILURE

EVIDENCE_FAILURE

EXPERIMENT_FAILURE

PATCH_FAILURE

REGRESSION_FAILURE

TOOL_FAILURE

ENVIRONMENT_FAILURE
```

例如：

```text
AI 找错代码：
RETRIEVAL_FAILURE

代码找对但理解错：
REASONING_FAILURE
```

# 四十、实施原则

整个实现过程中遵守以下原则：

### 原则 1

不要为了这个系统重新建设已经存在的 Code MCP、Document MCP、Bug MCP 和 Cloud Device 能力。

### 原则 2

不要把所有能力都做成 Skill。

### 原则 3

不要建立大量相互调用的 Agent。

优先：

```text
1 General Investigation Agent
+
少量独立 Reviewer Agent
```

### 原则 4

Workflow 管生命周期。

Agent 管推理。

MCP 管工具和数据。

Skill 管专业知识。

Validation Engine 管验证。

### 原则 5

Validation 不由主 Agent 自我裁判。

### 原则 6

历史案例不能直接当作当前 Bug 的答案。

### 原则 7

任何 Root Cause 都必须区分：

```text
Fact
Inference
Hypothesis
Confirmed Cause
```

### 原则 8

任何 Patch 都必须进行：

```text
Patch Scope Analysis
+
Original Bug Validation
+
Regression Validation
```

### 原则 9

验证失败必须能够重新进入 Investigation，而不是直接结束。

### 原则 10

所有过程必须产生 Trace，方便后续分析 AI 为什么失败。
